# 智能体与状态机设计

## 为什么采用“双层智能体”

时间触发、确认状态和家属待办必须可预测，因此由 TypeScript 规则层负责；自然对话、场景理解和可打断表达交给 MiniCPM-o 4.5。这样既利用全模态能力，又不让生成模型决定高风险业务状态。

| 层 | 职责 | 不负责 |
| --- | --- | --- |
| 确定性规则层 | 日程窗口、状态迁移、事件记录、家属待办 | 视觉语义和自然表达 |
| MiniCPM-o 会话层 | 持续看听、短句回复、主动纠正、打断恢复 | 药物/剂量判断、危险评级、身份认证 |

## 状态机

```text
idle
  └─ SESSION_STARTED → observing
       └─ ROUTINE_DUE → reminding
            └─ REMINDER_DELIVERED → awaiting_confirmation
                 ├─ USER_CONFIRMED → completed
                 └─ CONFIRMATION_TIMEOUT → needs_attention
                                               └─ FAMILY_ACKNOWLEDGED → completed

任意会话状态 ─ SESSION_ENDED → idle
```

“沉默”和“画面不清”不会触发紧急状态，只能进入 `needs_attention`。事件严重度也只使用信息、注意、重要三个级别，不输出医疗告警。

## 日程调度

服务端根据时区、星期掩码、开始/结束日期和本地时间生成唯一的日程实例，设备只读取当前可执行实例。客户端规则层在实例进入执行窗口时推进状态，并用日程实例与命令幂等键防止重复确认。提醒进入 `awaiting_confirmation` 后，系统继续按照 `familyNoticeMinutes` 计时；超时且仍无明确确认时自动转成家属待办。

真实 Provider 中，规则层会把到期事件作为一次受约束的模型动作请求发送给 MiniCPM-o；本地 Provider 使用 Chat HTTP 生成短提醒并由本地语音播放，公网 Provider 使用独立 Chat Realtime 音频响应。只有收到完整模型响应后才派发 `REMINDER_DELIVERED` 并允许本人确认；连接拒绝、提前关闭或超时都停留在失败状态，不会写成“已提醒”。

## 记忆注入

模型上下文来自四类已授权事实：

1. 长者称呼、居家标签和沟通偏好。
2. 授权联系人姓名与关系。
3. 启用中的药物日程：别名、时间、容器标签、位置和要求。
4. 最近维护的生活记忆，如眼镜位置和称呼偏好。

记忆正文由服务器加密保存。陪伴会话开始时，服务端依据家庭、陪伴对象、有效 Consent Snapshot 和设备权限生成最小必要的 `careSnapshot`，仅把本次允许使用的日程实例与记忆下发给已绑定设备；陪伴端不会从浏览器默认数据构造人物事实。

## Prompt 的硬边界

- 每次最多两句，一次只给一个步骤。
- 用户说话或场景变化时停止长解释，先响应当前情况。
- 只在日程到点、用户求助或任务相关标签清楚出现时主动说话。
- 不识别药片，不推断剂量，不诊断疾病。
- 画面或标签不清必须说“我还不能确认”。
- 不把沉默解释为危险。
- 不推断人的情绪、健康状态、年龄或身份。
- 人脸资料不用于自动认证。

## 事件可解释性

每个服务端事件记录标题、摘要、时间、来源类型、严重度、处理状态和关联日程实例。本人按钮/语音确认、设备超时、模型或规则动作和家属处理使用不同来源与幂等命令，家属看到的是事实摘要，而不是模型隐藏推理。

提供用户转写事件的本地 Provider 会把最终转写交给小型确定性意图分类器，只识别“完成”“再说一遍”“联系家属”三类闭环命令。分类器采用明确整句白名单，“还没完成”“不确定是否完成”“不要记录我完成了”和条件表达都不会闭环；只有 `awaiting_confirmation` 状态能接受确认。ModelBest 官方双工协议只返回模型的 `listen/text/audio` 输出，不返回用户转写，因此公网模式保留自然全双工对话，但业务闭环必须点击大按钮留痕，不引入未授权的第三方 ASR，也不从助手回复反推用户意图。

本人或家属完成任务时，服务端以日程实例为边界推进状态并关闭对应的开放待办，再新增来源明确的确认或处理记录。这样“模型/规则提出”“长者确认”和“家属关闭”不会混淆，也不会让已完成任务继续计入待查看。
