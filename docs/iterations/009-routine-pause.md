# 009：日程暂停与恢复（实施草案）

日期：2026-09-21；起点：`c02904c`；分支：`feat/iteration009-routine-pause`。

**状态：调研与三端实施草案，产品语义待确认；未开始业务实现。** 仅本地工作，不推送、部署或操作生产数据。第七轮用户确认的 `8de3879` 不作为本轮审查基线；本轮代码审查前另行固定范围。

## 1. 用户需求与依据

场景：陪伴对象临时离家，不确定何时回来。家属希望暂时停止某个日程，回来后沿用原来的时间、星期、内容及日期范围，不必删除重建。

已有编辑可以改变时间和起止日期，本轮不重复开发这些能力。[候选调研](009-routine-pause-research.md)核实：现有服务端只支持 ACTIVE / DELETED，Web 没有暂停操作，Android 的删除也不可恢复。可逆暂停是有条件成立的新增需求，而非现成接口换一个按钮。

竞品仅用于区分动作：Google Tasks 的“停止重复”不能恢复同一系列；Google Calendar 支持选择系列修改范围。二者不能证明已有可逆暂停，更不能代替本产品的实例处置规则。[Google Tasks 官方说明](https://support.google.com/tasks/answer/12132599?co=GENIE.Platform%3DDesktop&hl=en)、[Google Calendar 官方说明](https://support.google.com/calendar/answer/37115?co=GENIE.Platform%3DDesktop&hl=en)（2026-09-21 主审重新读取）。

## 2. 实施前的决策门

以下是推荐设计，不是用户已经批准的事实。异步问题无回复不能记作同意。

| 决策 | 推荐方案 | 当前状态 |
| --- | --- | --- |
| 暂停时如何处理已生成提醒 | 关闭 DUE / AWAITING_CONFIRMATION；保留待家属核验项及已有家庭待办，不伪造完成 | 已询问，待回答 |
| 恢复从何时开始 | 仅生成严格晚于服务端恢复生效时刻的实例，不补发暂停期间的提醒 | 与上一问题推荐选项一起询问，待回答 |
| 已运行会话是否需要同步 | 复核下一次客户端主动发送的提醒，并处理重复提醒和再次附带的日程上下文；不是只刷新管理卡片 | 2026-09-21 补充询问，待回答及运行时设计核实 |

两种暂停策略不能混合：如果选择“保留已生成提醒继续等待”，暂停后它们的展示、确认、升级及设备读取都必须继续受支持，现有 inactive→EXPIRED 逻辑不能直接套用。需先改写本草案，再实施。

**停止条件：** 上述影响真实提醒行为的选择未固定前，不添加 PAUSED 业务状态、数据库迁移或按钮，不以“只有新会话生效”的简版代替用户要求的在线会话支持。

## 3. 领域规则（按推荐策略设计）

### 3.1 日程与实例分开

- Routine 是长期安排，Routine Occurrence 是某次机会；暂停不是完成、删除或家属核验。
- 生命周期为 ACTIVE → PAUSED → ACTIVE；ACTIVE 或 PAUSED 均可删除，DELETED 不可恢复。
- 暂停保留 routine ID、内容、时区、星期、时间、起止日期及等待参数。历史实例、确认和待办不删除。
- 暂停中的日程仍可编辑配置，保存后仍为 PAUSED，不生成有效实例。这避免“原结束日期已过，必须先恢复才能编辑”的操作死路。恢复是独立的显式动作。
- ACTIVE 的编辑沿用原有契约；PAUSED 的编辑须复用版本与幂等保护，不把页面按钮开放等同于服务端已经支持。
- 未知状态显示中性“状态未知”，不提供暂停或恢复；不能把任意非 ACTIVE 状态都当成可恢复。

### 3.2 暂停后的实例与待办

| 暂停前 | 暂停提交后（推荐） | 恢复后 |
| --- | --- | --- |
| 未来或已到时的 DUE | EXPIRED，原因“日程已暂停”，version 增加，completedAt 不增加 | 不复活旧记录；新排期生成后续有效实例 |
| AWAITING_CONFIRMATION | 同上；旧客户端继续提交确认须失败或重放先前已成功的命令 | 不补发本次 |
| NEEDS_FAMILY_REVIEW | 保留，可以继续家属核验 | 保留 |
| CONFIRMED / EXPIRED | 不改变状态、确认或完成时间 | 保留 |
| OPEN / CLAIMED 家庭待办 | 保留状态和负责人 | 保留 |

暂停与本人确认、家属核验、升级并发时，以真实事务顺序为准：确认先提交则保留确认；暂停先关闭的项不能被旧版本确认复活；先升级的核验项保留，不能既创建待办又把它静默当作已完成。

### 3.3 恢复时间

- 恢复创建新的排期代际，旧排期永久失活；历史唯一键继续保持 `(scheduleId, scheduledAtUtc)`。
- 本代持久化 `effectiveFromUtc`，只允许 `scheduledAtUtc > effectiveFromUtc`。同一分钟已经过去的时间、恰好等于生效时刻的时间均不补发。
- 生效时刻是成功事务在取得日程锁后采样并保存的服务端时间，不是客户端时钟、请求刚进入时的时间，也不声称等于外部观察到的精确 commit 时刻；事务重试必须重新采样，重放沿用原收据。
- 不依赖调度器当前分钟取整，也不把 startDate 改成今天来冒充精确时间下界；重启后仍适用。
- 原日期范围无后续匹配（如过去的单次安排）时保持 PAUSED，返回可识别的“没有后续提醒时间”，用户在暂停状态编辑后再恢复。不得自动延长 endDate。
- 有无后续匹配的判断应复用既有 IANA 时区／夏令时算法，并给出有界搜索策略；不能只查 24 小时后就把每周日程判为过期。

上述新术语与规则暂留本草案。用户选择固定后再按 domain-modeling 技能更新 Household Care 词汇表；不把未批准状态写成现有领域事实。

## 4. Web 与 Android 页面设计

沿用项目设计系统及现有 React / 原生 Compose 页面；不迁移框架，不更换主题或导航。ui-ux-pro-max 仅用于状态、确认、错误恢复及无障碍检查，工具生成的新配色／字体不覆盖仓库 MASTER。

- 日程区域标题改为“日程安排”，仍在原位置；显示启用与暂停日程，暂停项不会消失。原提醒记录、最近动态、家庭待办保留。
- 卡片显示标题、原排期摘要及“已启用”／“已暂停”。暂停使用中性色和文字，不使用成功色暗示已完成。
- ACTIVE 卡片：编辑、暂停；PAUSED 卡片：编辑、恢复。Android 保留原删除入口并支持暂停项；不借本轮另给 Web 添加整套删除功能。
- 暂停二次确认标题“暂停这个日程？”，推荐正文：“暂停后，尚未确认的提醒将关闭。待家属核验记录和已有待办会保留。”按钮为“取消”“暂停日程”。在线会话的准确边界另用短说明，未确定前不发布“立即停止全部提醒”。
- 恢复确认显示原排期摘要和“只安排恢复后的提醒，不补发暂停期间的提醒”，按钮“取消”“恢复日程”。无未来时间时显示“原安排没有后续提醒时间，请先修改日期或重复规则”，提供编辑入口。
- 保存中／暂停中／恢复中禁用同一日程的冲突操作并显示进度；不提前乐观地宣布成功。收到成功收据但当前状态刷新失败时显示“操作已受理，状态暂未刷新”，提供刷新，不自动重复修改。
- 409 冲突提示“日程已被其他家属更新，请刷新后重试”；权限失败不得保留敏感明细。网络失败保留已授权的既有视图，并提供带相同幂等键的安全重试。
- 操作成功只刷新相关资源，保留 008 的日期／状态筛选；不把旧收据结果覆盖到已经恢复、再次暂停或切换后的工作区。
- 确认框绑定账号、家庭、长者、工作区 epoch、routine ID 与 version；切换／退出立即关闭，迟到响应不得弹回旧框或改写新页面。
- Web 支持键盘取消、焦点归还与可读错误；Android 采用现有对话框和 ≥48dp 点击区域。小屏和大字允许动作换行，不把标题挤到状态标签下面。

## 5. 服务端方案与代码可行性

### 5.1 命令与读取

拟新增 `POST /households/:householdId/routines/:routineId/pause` 和 `/resume`，请求含整数 version、必需 Idempotency-Key。沿用 MANAGE_ROUTINE、真实家庭／长者校验、当前授权和有界事务重试；不是 VIEW_EVENTS 或设备权限。

读取保留老接口默认 ACTIVE-only，新管理端使用显式 `includePaused=true`。查询参数严格验证；不得改变设备 current-occurrences 的含义。管理端暂停项投影最近保存的配置，不能只 include `active=true` 导致空卡片。

复用命令收据模块：指纹覆盖 actor、household、routine、目标动作和原 version。先核对当前权限，再读取可重放收据；PAUSED 或后来 DELETED 不应仅因 ACTIVE-only 查询让一次已经成功的旧命令变成无法识别的失败。重放不会复活删除项、回滚当前状态或绕过权限。

### 5.2 数据与历史

1. `ROUTINE_STATUS` 增加 PAUSED；字符串列不需要改成枚举。
2. `RoutineSchedule.effectiveFromUtc` 新增可空毫秒时间：既有排期为空时保留现有行为；恢复生成的新代际必填。迁移不能回填关闭或重写历史。
3. 暂停关闭原因不能仅存在于临时日志。拟为 occurrence 增加可空 `closureReason`，新暂停写 `ROUTINE_PAUSED`，旧记录为空仍显示“已关闭”；仅识别该明确原因时附短文本“日程已暂停”。两端读取兼容缺失／未知原因。
4. 暂停／恢复／暂停态编辑写既有加密内容、命令收据和 outbox 机制；outbox 保留操作者、前后版本与生效时间等必要审计字段，不包含明文家庭指令。历史事件是否新增用户动态不扩展为独立通知功能。

### 5.3 原子性与调度（必须先验证的技术点）

当前生成器在事务外读 schedules，再 `createMany`；只在暂停方法关一次旧数据不能防止在途生成回写。拟按单个 routine 建立共同的生命周期锁定顺序：routine → schedule → occurrence → 相关记录。暂停、恢复、编辑、删除、生成、推进、确认应遵循同一协议；不能只给新按钮加锁。

技术候选是短事务内对 routine 做参数化锁定读取，随后重读权威状态／排期并写入；事务外的候选 ID 只用于发现工作，不是写入授权。生成先提交则暂停关闭其结果；暂停先提交则旧代生成重读后不再写入。对 occurrence 路径可以先查归属 ID，再在事务锁定后重读，不能复用锁前的状态。

MySQL 官方文档说明锁定读取依赖事务、锁在提交或回滚后释放；这只是方案依据，不是本项目竞态已被证明正确。[MySQL 8.4 Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。实施前以当前 Prisma 7.9.1、真实 MySQL 8.4 隔离库验证参数化执行与锁顺序；不依赖内存 mutex 或 mocks 来证明跨进程互斥。

暂停本身必须一次提交关闭全部符合策略的实例，不依赖每分钟、每批 100 条的后台清理。事务超时／死锁按既有有界重试处理，不能循环到成功。不能在持锁事务内调用模型、网络通知或等待客户端。

最小模块接口围绕“执行一个带版本和幂等身份的生命周期命令”设计，调度所需的事务/锁定细节集中在内部 seam；不新增第二套通用工作流框架。原应用模块的 create/update/delete 方法保留可兼容入口。

- `care-workflow.types.ts`、`care-record.projection.ts`、Prisma schema/migration：新增字段的真实查询与投影，旧客户端缺省兼容。

- Android `FamilyApiContract.kt`、`LighthouseRepository.kt`、`LighthouseViewModel.kt`、`FamilyManagementScreen.kt`、model：同等状态与安全交互，保留原 routine operation lane。

## 6. 正在运行的陪伴会话

这是本轮可行性门，不是附带优化。补充调研须同时覆盖自动提醒、“再说一遍”、每次模型请求附带的 prompt、重连和原生双工初始化；仅验证家属页请求返回 200 不成立。

- 服务端暂停提交后开始的新权威读取必须排除该规则；恢复后的新读取只包含新代有效实例。
- 已发送给模型、正在播放或已经听到的内容不可追溯撤回。网络间隙与模型已有上下文也不能以“触发前多 GET 一次”承诺绝对零延迟撤回。
- 如果选择在线会话支持，应把“下一次主动发送前重新授权和取日程内容”作为确定性行为，失败不回退缓存指令，过期会话结果不发送。对普通对话中重新附带的旧日程上下文同样处理。
- 原生端必须先证实有没有本地主动调度路径；不能为通过验收编造现存能力，也不能悄悄新增整套定时语音提醒来冒充简单失效修复。
- 如果需求意味着强制中断现有模型上下文、重启会话或新双向推送协议，应回到决策门说明影响，不通过缩小承诺悄悄结项。

详细证据与候选方案见[运行时补充调研](009-routine-pause-runtime-research.md)。已核对的具体结论：

1. Web 自动提醒和“再说一遍”都要经过统一复核；仅保护自动 timer 会遗漏用户重播。当前“我完成了”有权威重查，不代表提醒发送也已有同等保护。
2. Web local/cloud 的独立 sendTurn 都再次附带初始化 prompt。v3/v4 prompt 的有界 actionableCare 即使不含当前目标，也可能包含另一条已暂停日程。候选方案是服务端提供不含日程的动作基础 prompt，发送时仅添加本次授权项；不使用字符串删除旧 JSON，也不回退旧完整 prompt。
3. current-occurrences 最多 32 条且含未来 DUE 和待家属核验项，不是播报许可。须检查 occurrenceId、状态、计划时刻及设备绑定；缺失抑制发送，但不能宣称一定是“已暂停”。对因截断缺失的有效项，完整在线保证需要补充可达的发现／精确复核契约，不能把漏播当成安全通过。
4. 恢复会产生新 occurrenceId。在线 Web 必须发现新项，不能只给旧缓存加复核；活动对象按 occurrenceId 区分，不得按同一个 routineId 错选旧实例。发现轮询使用 scoped single-flight，避免慢请求被周期性 latest-wins 永久淘汰。
5. 自动提醒与重播共享在途控制；一次读取失败不标“已提醒”，发送结果不确定时不自动重复播报。停止、重新绑定、会话替换和远程接管使旧请求失效；操作前及每次 await 后复核同一个 owner，不能用旧回调驱动新的 runtime。
6. 原生当前可追踪的是启动时发送 systemPrompt、之后持续音视频输入，没有找到本地 occurrence 定时触发。新会话过滤可验证；“暂停后当前双工模型也不再依据旧上下文主动表达”仍需模型会话刷新／重建或输出控制方案，不能宣称给一个不存在的定时器补检查即可实现。

因此“新的读取”和“当前模型输出停止”不是可互换的验收。上述候选只证明设计路径与风险；用户尚未选择生效范围，双工旧上下文与严格零迟到保证尚未解决，本草案仍不能作为完整批准的可执行规格。
